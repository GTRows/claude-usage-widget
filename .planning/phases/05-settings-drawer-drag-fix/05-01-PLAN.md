<objective>
Restore window-drag behavior while the settings drawer is open in normal (non-compact) mode. The widget's only drag region is `.title-bar` (`-webkit-app-region: drag` at `src/renderer/styles.css:177`). The settings drawer is rendered as `.settings-overlay` inside `.widget-container` with `position: absolute; inset: 0; z-index: 10;` (`src/renderer/styles.css:1729-1738`) — i.e. it stretches across the full widget surface, including the strip occupied by `.title-bar`. Even though the overlay itself opts out with `-webkit-app-region: no-drag` (line 181-183), the user-visible result is that once settings is open the title-bar pixels are covered by the overlay's `no-drag` rectangle, so the window can no longer be dragged from anywhere. After this plan: when settings is open and the app is in normal mode, the title-bar at the top of the widget continues to act as a drag handle exactly as it does when settings is closed; the overlay sits below the title-bar instead of underneath it. Compact mode is unchanged (compact has its own dedicated `compact-settings-overlay` and a different layout — out of scope).

Purpose: This is the only blocking UX defect surfaced for v1.15 outside of the auto-fire removal. Users who park the widget on a secondary monitor or on the right edge cannot reposition the window while reviewing settings, which forces a Done -> drag -> re-open cycle. The roadmap (`.planning/ROADMAP.md` Phase 5) calls this out as an "independent UI fix" with no dependencies; `STATE.md` lists it as the next phase after Phase 4 closeout. Phase 6 (manual update-check button) and Phase 7 (localization) both touch the settings drawer markup and benefit from the drawer being structurally clean before they land.

Output:
- Edit to `src/renderer/index.html`: move the `.settings-overlay` (and its sibling `.compact-settings-overlay`) out from underneath the title-bar so the title-bar's drag region is no longer occluded. Keep both overlays inside `.widget-container` (the existing absolute-positioning model relies on `.widget-container` as the offset parent), but constrain them to the area BELOW the title-bar via a CSS adjustment — markup change is one wrapper or, alternatively, no markup change at all and only a CSS `top` value tweak (see Task 1 for the diagnostic that determines which path).
- Edit to `src/renderer/styles.css`: change `.settings-overlay`'s `inset: 0` to a top-offset that matches the title-bar's rendered height (currently the title-bar has `min-height: 34px` plus a 1px `border-bottom`, so the overlay must start at the bottom of the title-bar — exact value to be measured in Task 1, but the expected value is `top: 35px; right: 0; bottom: 0; left: 0;` or, equivalently, switch to flex layout on `.widget-container` so the title-bar takes its natural height and the overlay fills the remainder). Apply the same fix to `.compact-settings-overlay` only if measurement shows the same occlusion bug exists in compact mode; otherwise leave compact untouched.
- No edits to `src/renderer/app.js`. The settings open/close flow, the SETTINGS_HEIGHT resize, the `setSettingsWindow` IPC, the `_settingsOpen` state, and the keyboard shortcut all keep working as-is. The bug is purely structural (overlay covers title-bar); no JS state needs to change.
- No edits to `main.js`, `preload.js`, schema, tests, or any other file. This is a 2-file (1 CSS, optionally 1 HTML) surgical fix.
- No new dependencies, no new IPC, no new files, no protected files modified.
</objective>

  <files>src/renderer/index.html,src/renderer/styles.css</files>
  <action>
Confirm the root cause and choose between two equivalent fixes.

Diagnostic steps (do these once, in `npm run dev` mode):

1. Open the widget. Confirm the title-bar is draggable from any non-button area (it is — `.title-bar { -webkit-app-region: drag; }` at `src/renderer/styles.css:177` is in effect).
2. Open the settings drawer (Ctrl+, or click the gear icon). Try to drag the window from the top strip where the title-bar is rendered. Confirm the window does NOT move. This reproduces the bug.
3. Open DevTools, inspect `.settings-overlay`. Confirm:
   - It has `position: absolute; inset: 0;` (computed style).
   - Its bounding rectangle's `top` is 0 — i.e. it starts at the same Y as `.title-bar`, not below it.
   - `getComputedStyle(document.querySelector('.settings-overlay')).webkitAppRegion === 'no-drag'`.
   - `document.elementFromPoint(50, 10)` (a point inside the title-bar strip while settings is open) returns the overlay (or one of its descendants), NOT `.title-bar`. This is the smoking gun: the overlay sits on top of the title-bar, and because the overlay is `no-drag`, it wins.
4. While still in DevTools, in the Elements panel temporarily set `.settings-overlay { top: 35px; }` (or any value >= the title-bar's `offsetHeight + 1`). Confirm:
   - The title-bar becomes visible above the overlay.
   - Drag now works from the title-bar strip with settings still open.
   - The settings content does not visually break — it should fill the area below the title-bar; the existing `.settings-content { height: 100%; }` makes the content fill whatever the overlay's box ends up being.
5. Repeat the same dragging test in compact mode (Ctrl+M then Ctrl+,). The compact mode uses `#compactSettingsOverlay` (a `.settings-overlay.compact-settings-overlay` element). Note whether the bug exists in compact mode too. (Expected: yes, same root cause — same `inset: 0` rule applies. But the goal phrasing in `ROADMAP.md` Phase 5 explicitly scopes the fix to "compact mode is off", so compact mode is OUT OF SCOPE for this plan unless step 5 reveals the compact title-bar is also draggable and also occluded. If compact's title-bar drag is already broken for unrelated reasons, log it as a follow-up and do not expand scope.)

Decision point: pick path A (CSS-only) or path B (markup-restructure).

- **Path A (preferred — CSS-only)**: change `.settings-overlay`'s `inset: 0` to `top: <title-bar-height + 1>; right: 0; bottom: 0; left: 0;`. Pros: zero markup churn, the existing `position: absolute` model is preserved, no risk of breaking the overlay's `::before` decoration or the inner `.settings-content` flex layout. Cons: hardcodes the title-bar height; if the title-bar's `min-height` ever changes, this value drifts.
- **Path B (markup-restructure)**: wrap `.title-bar` and the rest of the widget body in two siblings inside `.widget-container`, then make `.settings-overlay` a child of the second sibling instead of `.widget-container`. Pros: no hardcoded number. Cons: invasive markup change, risk of breaking the widget-container's `:hover` rules and `position: relative` behavior, larger diff, harder to review.

Pick Path A unless step 4 shows it visually breaks something. If Path A works in step 4 (it should), proceed. Path B is documented here only as a fallback — do not implement both.

For Path A, measure the exact title-bar height in DevTools while settings is closed:

```js
document.querySelector('.title-bar').getBoundingClientRect().height
```

The expected value is `34` (from `min-height: 34px`) — but use whatever the actual computed height is. If the value is non-integer (sub-pixel layout), round UP to the next integer. Add 1px to account for the `border-bottom: 1px solid var(--hairline)`. Final value goes into the CSS in Task 2.

Constraints:
- Do NOT introduce a CSS variable for the title-bar height in this plan unless one already exists. The renderer's CSS does not currently expose a `--title-bar-height` token; introducing one is a separate refactor that belongs to Phase 7's localization-touchup pass. A literal pixel value here is acceptable.
- Do NOT touch the `:hover` glow, the `::before` background gradient on `.settings-overlay`, or any other decorative rule.
- Do NOT modify `.title-bar` itself. The drag region is correct; the bug is on the overlay side.
- Do NOT change `z-index` of either element to "fix" the occlusion. z-index does not affect hit-testing for `-webkit-app-region` — Electron resolves drag/no-drag from the topmost element under the cursor. The fix is to physically move the overlay below the title-bar, not to re-stack it.
- Compact mode is OUT OF SCOPE per the roadmap's Phase 5 wording. If diagnostic step 5 finds the compact overlay also occludes a draggable region, log it as a deferred issue (`.planning/ISSUES.md` entry: trigger = "Phase 5 follow-up", owner = next planner) — do not expand scope.
