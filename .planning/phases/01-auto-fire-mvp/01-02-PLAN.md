<objective>
Build the web-session auto-fire channel: a main-process module that, when triggered, sends ONE minimal-cost request to claude.ai using the existing `sessionKey` cookie so the user's freshly-reset 5-hour window starts immediately. This plan also wires that module to the `'expired'` event from plan 01-01 with single-flight semantics, a debounce window, and a settings-driven on/off check.

Purpose: Deliver the actual "the next window starts immediately" behaviour. The trigger fires; this plan makes a real HTTP call land at claude.ai. After this plan, with the (still-default-off) feature flag flipped on by hand, an end user observes the next window opening within seconds of the previous one expiring.

Output: A new module `src/main/auto-fire/web-channel.js`, a thin dispatcher `src/main/auto-fire/dispatcher.js`, vitest specs for both, and a small wire-up patch in `main.js`. No renderer / preload / i18n work — those land in plan 01-03.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>How to send the auto-fire web-session request</decision>
  <context>The Claude.ai web app gates `/api/organizations/{org}/chat_conversations/.../completion` (and friends) behind Cloudflare. The existing read path uses `fetchViaWindow` (hidden BrowserWindow rendering JSON). For an auto-fire WRITE request, three options exist; this is the only choice that affects the rest of the plan.</context>
  <options>
    <option id="hidden-window-post">
      <name>Hidden BrowserWindow + fetch from inside the page</name>
      <pros>Same Cloudflare-bypass mechanism the read path already uses (proven to work); inherits cookies, UA, anti-bot signals automatically; no Node-level cookie wrangling.</pros>
      <cons>Heavier per fire (spawning a window for one request); we extend `fetch-via-window.js` rather than reusing it cleanly.</cons>
    </option>
    <option id="node-https">
      <name>Node `https.request` with `cookie: sessionKey=...` and the spoofed Chrome UA</name>
      <pros>Single tiny module, no BrowserWindow, easy to test by mocking `https`; mirrors the CLI fetch path (`src/cli/api.js`).</pros>
      <cons>Cloudflare may block writes more aggressively than reads; CLI `api.js` already detects HTML-as-block and we have no proof the write endpoint works without a real browser context.</cons>
    </option>
    <option id="renderer-fetch">
      <name>Have the renderer make the call from the visible widget window</name>
      <pros>Already inside a real Electron browser context (no second window).</pros>
      <cons>Breaks the rule "fire even when widget is unfocused / minimised" if the renderer is suspended; also crosses the trust boundary unnecessarily — auto-fire is a main-process concern.</cons>
    </option>
  </options>
  <resume-signal>
Default if no explicit response: `hidden-window-post`. Rationale: it inherits Claude.ai's Cloudflare bypass posture identically to the read path and matches the existing architecture. The remaining tasks below assume `hidden-window-post`. If the user picks `node-https`, swap Task 2's implementation to a `https.request` POST with `cookie: sessionKey=...; ...; user-agent: <CHROME_USER_AGENT>` and keep everything else the same.
  </resume-signal>
</task>

It mirrors the existing implementation: hidden BrowserWindow with `nodeIntegration: false, contextIsolation: true`, but instead of `loadURL(url)` it loads `about:blank` first, waits for `did-finish-load`, then runs `executeJavaScript` to perform a `fetch(url, { method: 'POST', credentials: 'include', headers: { 'content-type': 'application/json', ...injectedHeaders }, body: JSON.stringify(body) })`. Do NOT change `fetchViaWindow`'s signature. Do NOT introduce any new dependency. Keep the file under 200 lines (it's currently ~85; the additions should land it ~140).

Module exports become: `module.exports = { fetchViaWindow, postViaWindow, BLOCKED_SIGNATURES };` (export `BLOCKED_SIGNATURES` so tests and the dispatcher can reference the same constants).

<task type="auto">
  <name>Task 2: Create the web-session channel module</name>
  <files>src/main/auto-fire/web-channel.js</files>
  <action>
New CommonJS module exporting an async function `fireViaWebSession({ sessionKey, organizationId, post = postViaWindow, now = Date.now } = {})` that returns `{ status: 'ok' | 'skipped' | 'error', reason?, latencyMs }`. Inject `post` so vitest can stub the network without Electron.

Body:
1. Guard: if `!sessionKey || !organizationId`, return `{ status: 'skipped', reason: 'missing-credentials' }`. No throw — the dispatcher will log and move on.
2. Build the smallest plausible payload. The exact endpoint and JSON shape are not yet established in this codebase (`ROADMAP.md` Phase 1 lists "claude.ai web-session message-send endpoint + payload shape" as a research topic). For this plan use a constant block at the top of the file:

```js
const AUTO_FIRE_ENDPOINT = (orgId) =>
  `https://claude.ai/api/organizations/${orgId}/chat_conversations`;
const AUTO_FIRE_PAYLOAD = {
  // Smallest plausible "create empty conversation" body; replaced with the
  // real minimal message-send shape once research confirms the endpoint.
  // Reset-window trigger only requires that a billable interaction be charged
  // to the freshly-rolled 5-hour bucket; creating an empty conversation does
  // not count, so this constant is a placeholder until the message-send
  // endpoint is confirmed.
  name: '',
  uuid: null
};
```

Add a clearly-marked block comment above explaining: "Endpoint + payload are placeholders pending research per ROADMAP Phase 1. The dispatcher (Task 3) defaults the feature OFF; flipping the user setting on without finalising this constant is intentional dead code."

3. `const t0 = now();`
4. `const res = await post(AUTO_FIRE_ENDPOINT(organizationId), AUTO_FIRE_PAYLOAD, { headers: { cookie: 'sessionKey=' + sessionKey } });`
5. If `res.ok` (2xx), return `{ status: 'ok', latencyMs: now() - t0 }`.
6. On rejection, inspect the error message: if it starts with `CloudflareBlocked` / `CloudflareChallenge` / `UnexpectedHTML`, return `{ status: 'error', reason: 'session-expired', latencyMs: now() - t0 }`. Otherwise return `{ status: 'error', reason: 'transport: ' + err.message, latencyMs: now() - t0 }`.

Module size target: ~80 lines including the placeholder block comment. Pure (no Electron import — `postViaWindow` is injected so tests can substitute a `vi.fn()`).

Add `module.exports = { fireViaWebSession, AUTO_FIRE_ENDPOINT, AUTO_FIRE_PAYLOAD };`.
  </action>

<task type="auto">
  <name>Task 3: Create the dispatcher (single-flight, settings-gated, debounced)</name>
  <files>src/main/auto-fire/dispatcher.js</files>
  <action>
New CommonJS module exporting `createAutoFireDispatcher({ scheduler, getSettings, getCredentials, channels, now = Date.now, debugLog = () => {} })` that returns `{ start(), stop(), getStats() }`.

Inputs:
- `scheduler` — the `createAutoFireScheduler()` instance from plan 01-01.
- `getSettings` — `() => normalisedSettings` (calls `store.get('settings')` + `normalizeSettings` from `src/shared/settings-schema.js`).
- `getCredentials` — `() => Promise<{ sessionKey, organizationId } | null>` (the dispatcher does not know about `safeStorage`; main.js wraps the existing decrypt logic in a closure).
- `channels` — `{ webSession: fireViaWebSession }`. Plan 02-01 will add `apiKey`. Each value is the function to call.

Behaviour:
1. `start()` subscribes to `scheduler.on('expired', handler)`.
2. `handler(payload)` runs the dispatch pipeline:
   - Re-read settings via `getSettings()`. If `settings.autoFireEnabled !== true`, debug-log "[AutoFire] disabled — skipping" and return. (Even though plan 01-03 wires the UI, the schema key is added there. For 01-02 we read it via `settings.autoFireEnabled` and rely on `normalizeSettings` defaulting it to `false`. Add the key to the schema in plan 01-03; this read uses optional access so it returns `undefined` until then.)
   - Single-flight guard: if `state.inFlight === true`, debug-log "[AutoFire] already firing — skipping" and return.
   - Debounce guard: if `now() - state.lastFiredAt < DEBOUNCE_MS` (60_000), debug-log "[AutoFire] debounce window active — skipping" and return.
   - `state.inFlight = true; state.lastTriggerAt = now();`
   - Resolve `creds = await getCredentials()`. If null, record `{ ok: false, reason: 'missing-credentials' }` and unset `inFlight`.
   - Pick channel based on `settings.autoFireChannel || 'webSession'` (plan 02-02 will add the `apiKey` choice). If the channel is not in `channels`, record `{ ok: false, reason: 'unknown-channel' }` and unset `inFlight`.
   - `const result = await channel({ ...creds });`
   - Update `state.lastResult = result; state.lastFiredAt = now(); state.inFlight = false;`. Increment `state.successCount` on `ok` else `state.errorCount`.
   - Emit a debug log line summarising the result.
3. `stop()` removes the listener and disarms the scheduler. Used on app quit.
4. `getStats()` returns a snapshot of `{ inFlight, lastTriggerAt, lastFiredAt, lastResult, successCount, errorCount }`. Used by tests and (later) by a `get-auto-fire-stats` IPC if 01-03 wants to surface it.

Constants: `DEBOUNCE_MS = 60_000`. State lives in a closure object (no module-level mutation — each instance is independent so tests are isolated).

Module size target: ~120–150 lines.
  </action>
  <verify>vitest spec in Task 4 covers all branches; module export is `{ createAutoFireDispatcher, DEBOUNCE_MS }`.</verify>
  <done>Dispatcher routes events from scheduler to channel, honours settings, single-flight, and debounce. State accessible via `getStats()`.</done>
</task>

  7. Unknown channel name in settings → `errorCount === 1`, `lastResult.reason === 'unknown-channel'`.
