Expose a single user-visible on/off control for the auto-fire feature: add `autoFireEnabled` to the settings schema (default `false`), surface a toggle in the settings drawer, wire the IPC, and gate the new strings through whatever localisation seam exists today (i18n library is still TBD per `CONCERNS.md`, so we add the strings in a way that survives the eventual library choice without coupling to it).

</objective>

Find the corresponding save handler (where the always-on-top change calls `electronAPI.saveSettings({ alwaysOnTop: ... })` or sets it through `_savePartial`). Wire a `change` listener on the new checkbox:

```js
if (autoFireToggle) {
  autoFireToggle.addEventListener('change', async () => {
    const next = autoFireToggle.checked;
    await window.electronAPI.saveSettings({ autoFireEnabled: next });
    if (typeof _cachedSettings === 'object' && _cachedSettings) {
      _cachedSettings.autoFireEnabled = next;
    }
  });
}
```

Pattern follows what is already done for `compactMode` / `alwaysOnTop`. Do NOT add a separate IPC channel for this toggle; `save-settings` already accepts arbitrary keys and runs them through `normalizeSettings`, which now knows about `autoFireEnabled`.

No `main.js` changes (the dispatcher in plan 01-02 reads `settings.autoFireEnabled` on every expiry via its `getSettings` injection — flipping the toggle takes effect at the next event with no app restart).

  <action>

If a strings file already exists (search for `src/renderer/strings*.js`, `src/renderer/i18n*.js`, `locales/`, or a `t(` helper used in `app.js` / `bin/cli.js`): add the new keys (`settings.autoFire.label`, `settings.autoFire.hint`) to BOTH the Turkish and English string maps. Reuse the exact JSON / object shape already in use.
2. If no such file exists yet, add a tiny self-contained fallback in `src/renderer/app.js` near the top:

```js
const _AUTO_FIRE_STRINGS = {
  en: {
    'settings.autoFire.label': 'Auto-renew 5-hour window',
    'settings.autoFire.hint': 'When the active window resets, send a tiny request so the next window starts immediately.'
  },
  tr: {
    'settings.autoFire.label': '5 saatlik pencereyi otomatik yenile',
    'settings.autoFire.hint': 'Aktif pencere sıfırlandığında küçük bir istek göndererek bir sonraki pencerenin hemen başlamasını sağlar.'
  }
};
function _autoFireT(key) {
  const lang = (navigator.language || 'en').toLowerCase().startsWith('tr') ? 'tr' : 'en';
  return _AUTO_FIRE_STRINGS[lang][key] || _AUTO_FIRE_STRINGS.en[key] || key;
}
```

Then inside the existing settings-render path (or once on startup), walk the drawer's `[data-i18n]` nodes for the new keys ONLY (do not generalise this — that is the i18n library's job) and write `el.textContent = _autoFireT(el.dataset.i18n);` for the two specific keys. Leave a top-of-block comment: "Temporary inline strings until the i18n library decision is taken (see CONCERNS.md). Replace by the project `t(key)` helper when it lands."

The fallback is intentionally narrow: two keys, two languages, no generic loader. That keeps the surface small and easy to migrate.

Constraint: the static text already in the HTML from Task 2 acts as the English fallback if the t-helper bails — that means a user with a fresh, unfinalised i18n setup still sees a working English string, never an empty label or a raw key.
