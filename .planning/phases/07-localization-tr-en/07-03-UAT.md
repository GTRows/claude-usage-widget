# Phase 07-03 UAT — Settings drawer Language selector

## Preconditions

- App is logged in (sessionKey + organizationId resolved). If not, complete the login flow first; the settings drawer is not reachable from the login screen.
- Phases 07-01 and 07-02 are merged. The locale files contain the full key catalog (~110 keys per locale plus the four new `settings.language.*` keys from this plan).
- Run `npm start` from a clean checkout of the branch under verification.
- Settings drawer scrolling: the Appearance group is the SECOND group from the top; the Language row is the LAST row in that group, immediately under "Date format".

## Scenario 1 — Hot-swap tr -> en

1. App boots with `tr` as the active language (the project default, set by `SETTINGS_DEFAULTS.language` in `src/shared/settings-schema.js`).
2. Click the gear icon to open Settings.
3. Verify the drawer header reads **"Ayarlar"** (Turkish for "Settings"). The "Done" button reads **"Tamam"**.
4. Scroll to the Appearance group. Confirm the rows in order: Tema, Stil, Saat formatı, Tarih formatı, Dil. The "Dil" row's hint reads **"Arayüz dili. Değişiklik anında uygulanır."**
5. The dropdown shows **"Türkçe"** as the selected value, with **"English"** as the only other option.
6. Open the dropdown, click **"English"**.
7. Within ~200ms, the entire drawer should re-render in English:
   - Header: "Settings", "Done"
   - Group titles: Behaviour, Appearance, Tray, Thresholds, Data, Shortcuts, Updates
   - Appearance row hints: "Colour mode for the widget.", "Visual character of the widget.", "Clock display used throughout.", "How reset dates appear.", "Interface language. Applied instantly."
   - The Language dropdown still shows the same selected language name (always rendered in its own script — `Türkçe` and `English` stay literal regardless of UI language).
8. Close Settings (click "Done"). The widget body strings (metric labels, header tabs, range buttons) should already be English because `applyTranslations()` walked the whole DOM, not just the drawer. Verify "Current Session", "Weekly Limit", "Account Credits:" are visible in the appropriate places.
9. Right-click the tray icon. The menu items read **"Show Widget"**, **"Refresh"**, **"Log Out"**, **"Exit"**. The tray tooltip reads **"Claude Widget (GTRows)"** (intentionally untranslated, see 07-02 product-name decision).

PASS criteria for Scenario 1: every assertion in steps 3-9 holds. No console errors in the renderer DevTools. No console errors in the main-process terminal.

## Scenario 2 — Hot-swap en -> tr

1. Continuing from Scenario 1 (app is in English).
2. Open Settings, scroll to Language, switch to **"Türkçe"**.
3. Within ~200ms the drawer re-renders in Turkish — same expected strings as Scenario 1 step 4 (Tema, Stil, Saat formatı, Tarih formatı, Dil).
4. Close Settings. Body strings revert to Turkish: "Mevcut Oturum", "Haftalık Limit", "Hesap Kredisi:".
5. Tray menu in Turkish: "Pencereyi Göster", "Yenile", "Oturumu Kapat", "Çıkış". Tray tooltip still "Claude Widget (GTRows)".

PASS criteria for Scenario 2: every assertion in steps 3-5 holds. No console errors.

## Scenario 3 — Persistence across restart

1. Continuing from Scenario 2 (app is in Turkish).
2. Open Settings, switch to **"English"**, close Settings.
3. Quit the app fully (right-click tray -> Exit, OR `Ctrl+Q` if shortcut is bound, OR close from the dock). Do NOT just close the window — that hides it but the process keeps running.
4. Wait 2 seconds.
5. Re-launch with `npm start`.
6. Verify the FIRST PAINT of the widget is in English (no flash of Turkish before the swap). Specifically: the loading screen reads "Loading usage data..." not "Kullanım verisi yükleniyor...".
7. Verify the tray menu (right-click tray) reads English from the moment the menu first opens — no need to switch language to "wake up" the localization.
8. Open Settings, scroll to Language. The dropdown shows **"English"** as selected (the persisted value).
9. Switch back to **"Türkçe"** to leave the env in the project default (cleanup for the next run).

PASS criteria for Scenario 3: every assertion in steps 6-8 holds. The persisted language survives the full process restart. No flash of the wrong language at boot.

## Scenario 4 — Drawer state survives the swap

1. From either language, open Settings.
2. Type a value into the "Auto-refresh" input (e.g. `120`). Do NOT click Done yet.
3. Open the Date format dropdown to a non-default value (e.g. "Fri Mar 13").
4. Switch the Language dropdown to the OTHER language.
5. Verify:
   - The drawer is still open (it did not close).
   - The "Auto-refresh" input still shows `120` (the typed value was not lost).
   - The Date format dropdown still shows the user's chosen format (e.g. "Fri Mar 13" or "Cum 13 Mar" depending on language — but the SAME `data-i18n` option is selected).
   - The scroll position inside the drawer is preserved (Language row still in view).

PASS criteria for Scenario 4: drawer state, form values, and scroll position survive the swap unchanged. This validates the 07-02 "do NOT rebuild the DOM" decision.

## Failure-mode checks (negative assertions)

- After any swap, no element in the visible viewport shows a raw key path like `settings.language.label`. If you see a key string instead of a translated value, the locale file is missing that key — open `src/shared/locales/{tr,en}.js` and confirm Task 1's four keys landed in BOTH files.
- After Scenario 3 step 6, no flash of Turkish before English (or vice versa). If a flash IS visible, the boot order in `app.js:218-222` is broken: the renderer is calling `applyTranslations()` BEFORE `getLanguage()` resolves. Re-read the 07-02 decision "renderer boot order".
- The CLI (`npx claude-usage --help`) inherits the persisted language. After Scenario 3 step 6, run `npx claude-usage --help` from a separate terminal and verify the help text is in English. Switch the widget back to Turkish, re-run the CLI, verify Turkish output. (07-02 wires this; 07-03 simply exercises the path.)
