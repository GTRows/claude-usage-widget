Decisions recorded in this plan:
- **Selector control: native `<select>` matching the existing `timeFormat` / `weeklyDateFormat` / `trayStyleSelect` rows** — not a button-group like the Theme row, not a custom dropdown component. Reasoning: (1) the user's planning input explicitly says "a control similar to existing select dropdowns"; (2) the only other dual-option row in the drawer (`timeFormat` 12h/24h) uses a `<select>`, so two-option selects are precedent here; (3) a button group (Theme uses three buttons, Style uses five) would visually compete with Theme/Style in the same Appearance group; (4) `<select>` honours OS-level keyboard navigation (arrow keys, type-to-search) for free.
- **Placement: bottom of the Appearance group, BELOW Date format** — not a new top-level group, not under Behaviour, not under a new group called "Localization". Reasoning: (1) the Appearance group already collects every "how the widget LOOKS to the user" setting (Theme, Style, Time format, Date format); language is the same kind of presentation concern; (2) introducing a new group for one row adds visual fragmentation to a drawer that already has seven groups; (3) Behaviour is for what-the-widget-DOES (autostart, refresh interval, alerts), not for presentation. The bottom slot keeps the new row out of the drawer's first-paint viewport so the existing rows stay where users expect them.
- **Default language order in the dropdown: `tr` first, `en` second** — not alphabetical. Reasoning: `CLAUDE.md` makes Turkish the project default; the user's most frequent action is "confirm tr is selected" not "switch to tr". Putting `tr` first matches the default and the project's audience.
- **Option labels: language NAME in that language ("Türkçe", "English") plus an aria-friendly label key** — not BCP-47 codes (`tr-TR`, `en-US`) and not English-only labels ("Turkish", "English"). Reasoning: (1) the universal i18n convention is "show each language name in its own script" (so a user who can't read the current UI language can still find their language); (2) BCP-47 codes are noise to non-developers; (3) the option text itself goes through `data-i18n` so screen-reader users still get the active-language announcement via the `<select>` value.
- **No automatic broadcast piggy-backed on save-settings** — the renderer fires `setLanguage(value)` separately from `save-settings`. Reasoning: (1) `save-settings` already runs every 180ms via the live-save broker for any settings change (theme button, threshold input, etc.) — making `save-settings` ALSO broadcast `language-changed` would cause every save to re-walk the DOM, which is wasted work for settings-flips that are not language-related; (2) the existing `set-language` IPC has the single responsibility of "swap language now" and is the right seam to use; (3) flipping the select fires both `save-settings` (persistence) and `set-language` (live-update) because the `change` event listener calls the latter and the live-save broker handles the former — both run in the same tick, the user sees one swap.
- **Race between `save-settings` and `set-language`: irrelevant** — both IPC handlers in `main.js` write to the same store key (`settings.language`). The order they land does not change the final state because both write the same value. The `language-changed` broadcast fires from `set-language`; even if `save-settings` lands first, it does NOT broadcast, so the renderer hot-swap is driven exclusively by the `set-language` path. No need for sequencing logic.
- **First-run experience: tr is the active language and the selector reads "Türkçe"** — not a first-run dialog asking the user to pick. Reasoning: 07-01 already decided `'tr'` is the default per `CLAUDE.md`; a first-run dialog adds a step to onboarding that 99% of users skip past without changing. The selector is one click away in Settings for any user who wants `en`.
- **Hot-swap covers the settings drawer itself**: confirmed because the drawer's title (`settings.title`), every group title (`settings.group.*`), every label / hint (`settings.<row>.label` / `.hint`), every select option in `timeFormat` / `weeklyDateFormat` / `trayStyleSelect` / `exportHistoryRange` carries `data-i18n` from 07-02. The new `change` listener on `languageSelect` triggers the same `applyTranslations()` re-walk that everything else relies on. The drawer stays open during the swap because `applyTranslations()` writes textContent and attributes only — it does not rebuild any node, preserving the open/closed state and form values.
- **Tray menu hot-swap**: already handled by the 07-02 `language-applied-internal` event in `main.js`. When the renderer calls `setLanguage('en')`, main's `set-language` handler reapplies language, broadcasts `language-changed`, AND emits the internal event that rebuilds the tray menu. The new selector inherits this for free.
- **Persistence test**: confirmed because `save-settings` writes `settings.language` to electron-store, the `get-settings` handler returns it on next boot, `loadSettings()` hydrates the select, and `init()` (`app.js:218-222`) seeds the in-process language flag BEFORE the first `applyTranslations()` so the user-chosen language is the active language on app restart.
